# PolarHub Whitelabel Middleware Context

This repository is a **NestJS-based middleware (gateway)** project that wraps the PolarHub API.

## Core Principles

### 1. Middleware Design Principles (CRITICAL)
- **No hardcoding**: Do not hardcode values in the middleware code other than environment configuration.
- **Pass-through**: Only **transform** data received from the FE into the PolarHub API format.
- **No data addition**: The middleware must not add or modify data on its own (except for environment variable-based Agency settings).
- **Required data comes from FE**: Business data such as passenger information and contact information must be provided by the FE.
- **Use environment variables**: Agency settings (SiteCode, AgencyName, ContactInfoRefID) are managed via environment variables.
- **ContactInfoRefID auto-injection**: `sender.travelAgency.contactInfoRefId` is **always force-injected** from the environment variable (`POLARHUB_AGENCY_CONTACT_ID`).

### 1-1. API Common Principles (MUST FOLLOW)

#### TransactionID Pass-through
```typescript
// ✅ CORRECT - Pass through the transactionId received from FE as-is
const response = await client.orderRetrieve(orderId, {
  transactionId: request.transactionId,  // Provided by FE
});

// ❌ WRONG - Generated by middleware
const transactionId = generateTransactionId();  // Prohibited!
```

#### Auth Header Pass-through (HMAC Authentication)
```typescript
// If FE sends HMAC auth headers, use them as-is; otherwise generate from environment variables

// ✅ CORRECT - FE header pass-through or environment variable fallback
const headers = getOrGenerateAuthHeaders(
  { tenantId, apiSecret },  // Environment variables (for fallback)
  requestBody,
  feAuthHeaders,            // Headers sent from FE (Optional)
);

// Headers that FE can send:
// - x-date: RFC1123 timestamp (e.g., "Thu, 16 Jan 2026 06:51:52 GMT")
// - Digest: SHA-512 hash (e.g., "SHA-512={base64_hash}")
// - Authorization: HMAC signature (e.g., "hmac username=...")
```

**Auth Header Priority:**
| Priority | Condition | Behavior |
|----------|-----------|----------|
| 1 | FE sends x-date, Digest, Authorization **all three** | Use FE headers as-is |
| 2 | FE headers missing or incomplete | Generate HMAC from environment variables |

> **Note**: `X-Tide-Tenant-Id` header is **always** added unconditionally (from `POLARHUB_TENANT_ID`) in both paths above. It identifies the tenant for whitelabel multi-tenant support.

#### HTTP Method - All APIs use POST
```typescript
// Per PolarHub API HTTP spec, all APIs use POST
@Post('retrieve')  // OrderRetrieve
@Post('cancel')    // OrderCancel
@Post()            // OrderCreate, AirShopping, etc.
```

#### Sender (FE value takes priority, environment variable fallback)
```typescript
// Sender: Can be sent from FE (Optional)
// Priority: FE value > env var > skip (not included)

// ✅ CORRECT - Sender sent from FE (all fields used as-is)
{
  "sender": {
    "travelAgency": {
      "agencyId": "AGENCY_001",
      "siteCode": "01",
      "agencyName": "My Travel Agency",
      "contactInfoRefId": ["CTC_TA1"]
    }
  },
  "transactionId": "...",
  "orders": [...]
}

// ✅ CORRECT - When Sender is omitted, built from env vars (missing env vars are skipped)
{
  "transactionId": "...",
  "orders": [...]
}
// → Sender is built using POLARHUB_TENANT_ID, SALES_BRANCH_ID, POLARHUB_AGENCY_CONTACT_ID (all optional)
```

#### Sender Priority
| Field | Priority | Behavior |
|-------|----------|----------|
| agencyId | FE > POLARHUB_TENANT_ID | FE value takes priority; falls back to env var |
| siteCode | FE > SALES_BRANCH_ID > skip | FE value > env var > not included |
| agencyName | FE > POLARHUB_AGENCY_NAME > skip | FE value > env var > not included |
| contactInfoRefId | FE > POLARHUB_AGENCY_CONTACT_ID > skip | FE value > env var > not included |

#### PointOfSale
```typescript
// PointOfSale: Default 'KR' or sent from FE
PointOfSale: options?.pointOfSale || 'KR'
```

#### ContactInfo Pass-through (CRITICAL)
**Contact information is passed through exactly as received from FE. Do not modify the data.**

```typescript
// ❌ WRONG - Data modification in middleware is prohibited!
Phone: [{
  CountryDialingCode: ci.phone.countryDialingCode || '82',  // Fallback prohibited
  PhoneNumber: `+${ci.phone.countryDialingCode}${ci.phone.phoneNumber}`,  // Concatenation prohibited!
}],

// ✅ CORRECT - FE data pass-through
Phone: [{
  ...(ci.phone.label && { Label: ci.phone.label }),  // Sent from FE
  CountryDialingCode: ci.phone.countryDialingCode,   // Pass through as-is
  PhoneNumber: ci.phone.phoneNumber,                  // Pass through as-is
}],
```

**Prohibited actions**:
- Do not prefix country code onto phoneNumber
- Do not process data with `.replace()` or similar methods
- Do not set default (fallback) values (FE must send required values)
- Do not hardcode data values for Label, CountryCode, etc.

### 1-2. No Hardcoding of Data Values (CRITICAL - Added 2026-01-15)

**Business data must not be embedded directly in the code.**

| Item | ❌ Prohibited | ✅ Correct approach |
|------|--------------|---------------------|
| Country code | `CitizenshipCountryCode: 'KR'` | `pax.citizenshipCountryCode` (Sent from FE) |
| Phone Label | `Label: 'Mobile'` | `ci.phone.label` (Sent from FE) |
| Residence country | `ResidenceCountryCode: 'KR'` | `pax.residenceCountryCode` (Sent from FE) |

```typescript
// ❌ WRONG - Hardcoding defaults when IdentityDoc is absent
: {
    CitizenshipCountryCode: 'KR',  // Hardcoding prohibited!
    ResidenceCountryCode: 'KR',    // Hardcoding prohibited!
  }

// ✅ CORRECT - Receive from FE and pass through
: {
    ...(pax.citizenshipCountryCode && {
      CitizenshipCountryCode: pax.citizenshipCountryCode,
    }),
    ...(pax.residenceCountryCode && {
      ResidenceCountryCode: pax.residenceCountryCode,
    }),
  }
```

**Allowed defaults**: Only environment variable-based Agency settings are allowed
```typescript
// ⚠️ Allowed - Environment variable fallback
siteCode: this.configService.get('polarhub.siteCode') || '01',
pointOfSale: options?.pointOfSale || 'KR',  // Environment variable-based fallback allowed

// ❌ Prohibited - Business data defaults
Label: 'Mobile',  // Hardcoded!
CitizenshipCountryCode: 'KR',  // Hardcoded!
```

### 1-3. Travel Agency ContactInfo Optional Injection (Updated 2026-03-24)

> **Priority**: FE value > env var (`POLARHUB_AGENCY_CONTACT_ID`) > skip (not included)

#### Injection Behavior
- FE provides contactInfoRefId in sender → Use FE value as-is
- FE does not provide, env var is set → Inject env var value
- Neither provided → Skip (not included in request)

#### ContactInfoList in OrderCreate
- FE provides contactInfoList → Use FE list as-is
- FE omits contactInfoList, env vars (POLARHUB_AGENCY_CONTACT_ID + AGENCY_EMAIL, etc.) set → Auto-build agency contact
- Neither provided → Skip (ContactInfoList not included)

```typescript
// polarhub.service.ts - transformSender method
private transformSender(sender?: BaseParams['sender']): Sender {
  const agencyContactId = this.configService.get<string>('POLARHUB_AGENCY_CONTACT_ID');

  if (!sender) {
    return {
      TravelAgency: {
        AgencyID: defaultTenantId,
        ...(defaultSiteCode && { SiteCode: defaultSiteCode }),
        ...(agencyContactId && { ContactInfoRefID: [agencyContactId] }),
      },
    };
  }

  // FE value > env var > skip
  return {
    TravelAgency: {
      AgencyID: sender.travelAgency.agencyId,
      ...(sender.travelAgency.contactInfoRefId?.length
        ? { ContactInfoRefID: sender.travelAgency.contactInfoRefId }
        : agencyContactId ? { ContactInfoRefID: [agencyContactId] } : {}),
    },
  };
}
```

#### Travel Agency ContactInfo Structure
This is the travel agency contact information configured via environment variables. This information can be included in ContactInfoList as CTC_TA1.


### 1-6. Payment Type Conversion Rules (CRITICAL - Added 2026-02-03)

> **MUST**: When using simplified DTOs (type field) in Controllers, you must convert them with `transformPaymentList`!
> If passed to the Service without conversion, `type: 'Ag'` will be incorrectly converted to `type: 'Cash'`.

#### Problem Scenario

The Service's `buildPaymentList` determines Payment Type based on the `paymentMethod` object:
- If `paymentMethod.card` exists → `Type: 'Card'`
- If `paymentMethod.agentDeposit` exists → `Type: 'Ag'`
- If neither exists → `Type: 'Cash'` (default)

If a simplified DTO (with only the type field) is passed to the Service without conversion, `paymentMethod` is empty and always defaults to `Cash`.

```
FE Request: { type: 'Ag', amount: 100 }
         ↓ (Passed without conversion)
Service: paymentMethod is empty → Defaults to 'Cash'
         ↓
PolarHub: { Type: 'Cash', Amount: 100 }  ← Not the intended result!
```

#### Correct Conversion

```typescript
// ❌ WRONG - type field is ignored and converted to Cash
paymentList: request.paymentList

// ✅ CORRECT - Create paymentMethod object based on type
paymentList: this.transformPaymentList(request.paymentList)

/**
 * PaymentList conversion (DTO → Service)
 *
 * CRITICAL: Must set the appropriate paymentMethod based on type
 * - Cash → cash: { cashPaymentInd: true }
 * - Ag → agentDeposit: { agentDepositId: '' }
 * - Card → card: { ... } (Extend when card details are needed)
 */
private transformPaymentList(paymentList?: PaymentDto[]) {
  if (!paymentList) return undefined;

  return paymentList.map((p) => ({
    paymentMethod: {
      cash: p.type === 'Cash' ? { cashPaymentInd: true } : undefined,
      agentDeposit: p.type === 'Ag' ? { agentDepositId: '' } : undefined,
      // Card requires card details (cardNumber, etc.), implement after DTO extension
    },
    amount: {
      currencyCode: p.curCode,
      amount: p.amount,
    },
    orderItemId: p.orderItemId,
    offerItemId: p.offerItemId,
    paxRefId: p.paxRefId,
  }));
}
```

#### Where to Apply

| Controller | Required | Reason |
|------------|----------|--------|
| OrderController (OrderCreate) | ❌ Not needed | DTO already uses paymentMethod structure |
| **OrderChangeController** | ✅ **Required** | Uses simplified PaymentDto (type field) |
| OrderQuoteController | Depends on the case | Need to check DTO structure |

### 4. API Spec Validation Principles (CRITICAL)

> **MUST**: Always verify field types in the OpenAPI spec before implementing DTOs/Services.

#### Field Type Verification Required

4. **$ref tracking**: Trace reference types to their actual definitions

## DTO Generation and Maintenance Rules
- **File location**: `src/dto/{api-kebab}.dto.ts` (e.g., AirShopping → `src/dto/air-shopping.dto.ts`)
- **Basic structure**: For each API, create two class DTOs: one for request (RQ) and one for response (RS). (e.g., `AirShoppingRQDto`, `AirShoppingRSDto`)
- **Decorator usage**: Include `class-validator`, `class-transformer`, and `@nestjs/swagger` decorators following NestJS standards.
- **Type mapping**:
  - `string` → `string`
  - `integer`/`number` → `number`
  - `boolean` → `boolean`
  - `array` → `Type[]` (try to infer specific types when possible)
  - Complex types (`allOf`, `oneOf`, `anyOf`, deep `$ref`, etc.) are initially handled as `any` or `unknown` with a `// TODO` comment.
- **Scope of work**: When creating/updating DTOs, focus on only one API context at a time.

### DTO Nested Object Decorator Rules (CRITICAL)

> **MUST**: Nested objects must **always** use both `@ValidateNested()` and `@Type()` decorators together.

```typescript
// ❌ WRONG - Without @Type(), class-transformer will not work
@ValidateNested()
nestedField?: NestedDto;  // Remains as plain object at runtime

// ❌ WRONG - Inline types are prohibited
@ValidateNested()
nestedField?: { someProperty: string };  // class-transformer will not work

// ✅ CORRECT - Explicit class + @Type() required
@ValidateNested()
@Type(() => NestedDto)
nestedField?: NestedDto;

// ✅ CORRECT - For arrays
@ValidateNested({ each: true })
@Type(() => ItemDto)
items: ItemDto[];
```

### 1-9. Error Pass-through Architecture (CRITICAL - Added 2026-02-13)

> **MUST**: PolarHub API errors must be passed through to FE with `ResultMessage` format intact.

#### Global Exception Filter

`PolarHubExceptionFilter` is registered as a global filter in `main.ts` and catches all `PolarHubError` exceptions automatically.

```typescript
// main.ts - Global filter registration
app.useGlobalFilters(new PolarHubExceptionFilter());
```

**Controllers do NOT need manual try/catch for PolarHub errors.** The filter handles them globally.

```typescript
// ❌ WRONG - Manual error conversion in controller (no longer needed)
try {
  const result = await this.polarHubService.someApi(params);
  return result;
} catch (error) {
  throw toHttpException(error);  // Unnecessary!
}

// ✅ CORRECT - Let PolarHubError propagate to global filter
const result = await this.polarHubService.someApi(params);
return result;
```

#### FE Response Format

```json
// Error response (e.g., PolarHub 50101)
{
  "statusCode": 400,
  "message": "Invalid request",
  "ResultMessage": {
    "Code": "50101",
    "Message": "Invalid request",
    "MessageDetail": {
      "Errors": [{ "Owner": "SQ", "Message": "No available flights" }]
    }
  }
}

// BA 50202 special case → HTTP 200
{
  "statusCode": 200,
  "message": "booking has been created with warnings",
  "ResultMessage": {
    "Code": "50202",
    "Message": "booking has been created with warnings",
    "MessageDetail": { ... }
  }
}
```

#### Error Flow
```
PolarHubClient → throws PolarHubError → PolarHubExceptionFilter → FE response
                                        (maps error code to HTTP status)
```

- `npm run test`: run the Jest test command (currently passes even when no test files are present)

Optional maintainer commands:

- `npm run sync:llms:index`: refresh `spec/schema-llms-index.json` from the external `llms.txt` source
- `npm run gen:dto:llms`: generate DTO scaffolding from the bundled schema index workflow

The `sync:llms:index` and `gen:dto:llms` scripts are maintenance helpers. They are not required for normal local startup or day-to-day API usage.
